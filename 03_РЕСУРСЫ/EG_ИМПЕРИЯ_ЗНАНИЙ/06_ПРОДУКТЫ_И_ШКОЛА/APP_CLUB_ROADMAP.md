## 2. Почему не строить нативное «с нуля» прямо сейчас

Уже зафиксировано в пульте: сначала живая воронка (тест → курс → клуб), Mini App / тяжёлый продукт — позже.

Приложение имеет смысл, когда:

1. Клуб стабильно продаётся и удерживает (Tribute или web).  
2. Есть понятный еженедельный контент-ритм.  
3. Есть бэкенд: пользователи, подписка, доступ к урокам.

До этого — **PWA / улучшенный web-клуб** дешевле и быстрее проверяет продукт.

## 3. Архитектура (рекомендация)

```text
Один продукт-клуб
        │
        ├── Web (egoshev.ru/club + кабинет)
        ├── Telegram (Tribute / Mini App — вход RU)
        └── Native shell (App Store + Google Play)
                 └── тот же API / тот же контент
```

**Стек (рабочая гипотеза, не догма):**

| Слой | Вариант A (быстрее в сторы) | Вариант B (дольше, «нативнее») |
|---|---|---|
| UI | Next.js кабинет + **Capacitor** / PWA | Flutter или React Native |
| Backend | существующий сайт + отдельный Club API | тот же |
| Видео | Kinescope / аналог с RU + CDN | то же |
| Auth | email + Apple/Google Sign-In | то же |
| Аналитика | свой кабинет + Amplitude/PostHog | то же |

> 💡 Для EG оптимальнее **Вариант A**: один код клуба → обёртка в сторы. Не плодить три продукта.

## 4. Оплаты: Россия и мир (критично)

Один провайдер на всё **не сработает**. Нужна **двухконтурная** модель.

| Регион | Модель | Примеры |
|---|---|---|
| **Россия** | Внесторовая подписка (web / deep link) где позволяют политики + локальный эквайринг | Prodamus · Tribute · CloudPayments / аналоги |
| **Мир (вне РФ)** | Store IAP там, где Apple/Google требуют для digital goods +/или Stripe web | App Store IAP · Google Play Billing · Stripe |

**Правила:**

- В приложении для digital subscription сторы часто **требуют** IAP (особенно Apple) — закладывать комиссию 15–30%.  
- Для РФ держать **web-оплату клуба** как основной контур (как сейчас Tribute), приложение — доступ и опыт.  
- Юрлицо / ИП, договоры с Apple/Google Developer, налоговый контур — отдельный блок с бухгалтером.  
- Цена в сторах: рубли (RU) + USD/EUR (global); SoT цены по-прежнему в `products.yaml`, стор-цены — производные.

**Не обещать** «одна кнопка Pay везде без нюансов» — это иллюзия.

## 5. App Store + Google Play · доступность в РФ и мире

| Тема | Реальность |
|---|---|
| Публикация в сторах РФ | Обычно возможна при выполнении требований аккаунта разработчика |
| Платежи Apple/Google в РФ | Ограничения и изменения политик — закладывать **внесторовую** оплату для RU |
| Контент/CDN | Видео и API должны открываться из РФ и из-за рубежа (свой CDN / провайдер с RU-нодой) |
| Возраст / Health | Не позиционировать как медприложение; без диагнозов и «лечения» — иначе Review risk |
| Аккаунты | Apple Developer (юр/физлицо) · Google Play Console · возможно отдельный entity для global |

Чеклист до первой подачи: Privacy Policy · Terms · Account deletion · Support URL · скриншоты без медобещаний · возрастной рейтинг.

## 6. MVP приложения (что внутри v1)

Минимум, чтобы это был **клуб**, а не лента:

1. Вход / регистрация  
2. Статус подписки (активна / нет → оплата)  
3. **План недели** (главный экран)  
4. Уроки / тренировки по дням  
5. Прогресс (отметил выполнение)  
6. Библиотека (вторична)  
7. Уведомления: «сегодня блок»  
8. Профиль + поддержка (Telegram / email)

**Не в v1:** соцсеть, AI-тренер, магазин мерча, 10 языков, офлайн-весь каталог.

## 7. Этапы (90 → 180 дней)

| Фаза | Срок | Результат | Деньги/фокус |
|---|---|---|---|
| **0. Фундамент** | сейчас–30 дн | Клуб стабилен в Tribute/web · еженедельный ритм · воронка тест→курс→клуб | Не кодить сторы |
| **1. Club Web MVP** | 30–60 дн | Личный кабинет клуба на сайте (план недели, доступ по подписке) | Один продукт, web |
| **2. PWA** | 60–90 дн | «Добавить на экран» · пуши по возможности | Проверка привычки |
| **3. Store shell** | 90–150 дн | Capacitor → TestFlight + Internal testing Play | Аккаунты разработчика |
| **4. Global** | 150–180 дн | IAP/Stripe контур · EN минимум · цены USD | Мир без ломки RU |

Параллельно **не** запускать второй клуб в Telegram с другой логикой.
